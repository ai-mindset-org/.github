# Публичные репозитории AI Mindset

Правило применяется к публичным репозиториям `ai-mindset-org`, их README, публичной
документации, статическим HTML-ссылкам и профилю организации. Владелец материала
сохраняет ответственность за публичное происхождение текста и человеческую приёмку.

## Создание и публикация репозитория

1. Указать назначение проекта и корректный статус: действующий инструмент, пример
   или архив. Сохранить источники, лицензии и исторические даты.
2. Добавить стандартный блок со ссылками на лабы и базу знаний в начале README,
   сразу после названия или баннера. В `.github` он нужен также в `profile/README.md`.
3. Ссылки, по которым читатель выходит к публичным инструментам и сайтам AIM,
   должны иметь UTM. Читатель видит обычную короткую подпись; параметры находятся
   в адресе ссылки. Не показывать длинную UTM-строку вместо подписи.
4. Подключить workflow `Public repository links` из шаблона организации и выполнить
   проверку локально или в CI. Шаблон сам не устанавливается в новые репозитории.
5. В About сохранить назначение и адрес собственного демо. В description добавить
   единый суффикс ` · Labs: go.aimindset.org/<repo-labs-slug>`. Website ведёт через
   короткую ссылку на прежнее демо, а если демо не было – на раздел лаб. Параметры
   находятся в цели редиректа, поэтому в карточке нет длинной UTM-строки.
   Публичная страница организации сохраняет основной сайт в качестве цели Website.

Видимый блок:

> Лабы AI Mindset · База знаний

Первая ссылка ведёт на раздел обучения основного сайта с якорем `#learning`.
Так ссылка остаётся актуальной при смене потока. Это не утверждение о наборе
в конкретную архивную лабу. Баннеры и остальная структура README сохраняются.

## UTM

Используется существующий словарь AIM:

| Параметр | Правило |
|---|---|
| `utm_source` | `website` – совместимое значение; `github` не добавляется в словарь молча |
| `utm_medium` | `article` |
| `utm_campaign` | существующий slug продукта; для общей линейки и инструмента без отдельного продукта – `start`; для bio – `bio` |
| `utm_content` | `github-<repo>`; допустим дополнительный суффикс места размещения; 2–48 символов `[a-z0-9._-]` |
| `.github` | `utm_content=github-org-profile` |
| `utm_id` | только реальный Id существующей строки командного сервиса UTM |

Пример синтаксиса, не новая зарегистрированная метка:

```markdown
[Открыть инструмент](https://apps.aimindset.org/example/?utm_source=website&utm_medium=article&utm_campaign=start&utm_content=github-example)
```

Сохранять значимые query-параметры и фрагмент: режим демо, выбранный продукт,
якорь раздела. Не использовать `utm_term`. Не придумывать Id. Сырые UTM дают
аналитику переходов; они не доказывают сквозную атрибуцию бота, заказа или оплаты.

Зарегистрированные ссылки с `utm_id` и промокодом нельзя перемечать под
репозиторий: это может сломать партнёрскую атрибуцию. Проверка сохраняет полную
метку и требует ручного разбора неполной. Наличие строки в сервисе UTM CI не
подтверждает. Короткие ссылки `go.aimindset.org` создаются через существующий
сервис, а не имитацией редиректа в этом репозитории.

Для About настройки записываются в `.github/public-links.json`: идентичность
репозитория, короткая ссылка лаб, website и его точная цель. CI читает реальные
публичные поля GitHub и проверяет HEAD→302→Location без записи клика.
Нельзя просто дописывать UTM к адресу `go`: работают параметры сохранённой цели.
В этом контуре используются сырые UTM для посещений; для атрибуции заказа
дополнительно требуется настоящая строка канонического UTM-сервиса.

## Область автоматической проверки

Проверяются tracked Markdown (`.md`, `.markdown`, `.mdx`) и статические
`<a href>` в HTML (`.html`, `.htm`). Включены inline/reference-ссылки,
кликабельные картинки, обычные URL и HTML-якоря в Markdown. Label обычной
ссылки не меняется; голый URL превращается в Markdown-ссылку с чистым адресом
в подписи. HTML-атрибуты и подписи сохраняются, амперсанды экранируются.

Не перемечаются картинки, CSS/JS, JSON/XML, архивы и PDF, API/auth endpoints,
примеры в fenced/inline code, сторонние сайты, GitHub source links,
Telegram deep links и служебные домены. Динамически вычисляемые ссылки в JS/JSX
и ссылки внутри скачиваемых PDF требуют отдельной проверки при их изменении.
Ссылки с подписью/токеном не исправляются автоматически. Симлинк документации
или превышение лимита 4 MB на файл дают ошибку, а не неполный PASS.

Проверка не выполняет код, package scripts, установку зависимостей или сетевые
запросы из проверяемого репозитория. Её можно запускать без секретов и доступа
к аналитике. Она не измеряет рост и не проверяет доступность каждой цели по HTTP.

## Команды для человека и агента

Из доверенного checkout этого репозитория:

```bash
python3 tools/public_links.py --repo <checkout> --slug <repository-name> --json
python3 tools/public_links.py --repo <checkout> --slug <repository-name> --fix
python3 tools/public_metadata.py --repo <checkout> --slug <repository-name> --json
python3 -m unittest discover -s tests -v
```

`--fix` меняет только допустимые ссылки в документации и стандартные README-блоки.
После него просмотреть diff, проверить публичные источники и целевые страницы,
затем повторить команду без `--fix`. Неполную зарегистрированную ссылку разобрать
через канонический UTM-процесс, не снимать ошибку подменой параметров.

## CI и обновление канона

Общая реализация находится в `tools/public_links.py`; reusable workflow –
`.github/workflows/public-links-reusable.yml`. Потребители закрепляют полный
commit SHA workflow. Сам workflow читает код проверки из фиксированного SHA,
а проверяемый PR – только как данные. `contents: read`, без секретов,
`pull_request_target`, сетевых вызовов к аналитике и запуска кода потребителя.

Новая версия проверки проходит тесты на реальном CLI и отрицательные примеры,
включая удалённые/неверные UTM. После приёмки обновляется pin потребителей.
Факт наличия check не меняет branch protection: требование обязательного check
задаётся отдельной политикой владельца, существующие защиты не ослабляются.
